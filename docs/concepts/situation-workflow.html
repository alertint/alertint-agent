How AlertINT handles a Situation

One operator view from durable alert receipt to investigation, expected maintenance, recovery, and recurrence. Expectedness changes assessment; it never changes what the monitoring source says.

1. From webhook to operator view

1 · Receive

Alertmanager or Zabbix sends one alert or a batch.

204 only after the delivery and pending dispatch are committed. Invalid input gets 400; unavailable storage gets retryable 503.

2 · Group

A retry with the same delivery identity is a no-op. A new delivery joins or opens an Incident by the receiver grouping identity.

A terminal Situation is never reopened; later firing starts a linked Situation.

3 · Observe

Bounded source checks gather current evidence. Each result says present, absent, unsupported, unavailable, or stale.

Failures remain visible and retry on their durable schedule.

4 · Assess

Deterministic lifecycle rules run first. Acute Triage and Situation assessment run only when due and within their persisted budgets.

Stale results cannot overwrite newer state.

5 · Present

Slack has one root per Situation: title, lifecycle/status, then Finding. Meaningful transitions go to its thread.

MCP exposes current records, transitions, evidence, delivery state, and operator decisions.

2. Lifecycle and recovery

Active

At least one monitored condition is firing, or investigation work is still relevant. Repeated unchanged telemetry does not create a new episode.

Confirming recovery

All required source states are clear. The persisted grace period must finish while clearance remains authoritative.

Recovered

Terminal. Monitored alerts stayed clear through grace. Monitoring for this episode ends.

New linked Situation

A later firing after a terminal end gets a new root and links to prior history. The old Situation stays immutable.

Refire during grace

Return to Active, name the refiring alert, and resume the actual current action. Do not claim a new triage run unless one is scheduled.

Source truth disappears

Missing truth never proves recovery. If the lifecycle deadline expires without fresh authoritative firing, the Situation can end as Closed unknown.

Work fails

Retries and final limitations remain explicit. Investigation failure alone does not fabricate a Finding or recover the Situation.

Monitoring continues

Routine checks update durable state without posting heartbeat messages. Slack changes only for operator-relevant transitions.

3. Expected maintenance is a separate decision

Expectedness overlays the active condition

An operator may mark the current non-critical condition expected until a time, or confirm a reusable schedule for an exactly proven source rule and scope. The Finding stays visible. Monitoring, evidence collection, investigation, source recovery, and recovery grace continue normally.

Still applies

Same proven rule, scope, condition, and allowed urgency. Unchanged repeats do not ask for the same decision again.

Stops applying

Expiry, withdrawal, changed rule/scope/condition, criticality, or independent urgency restores normal assessment. Slack states the reason.

No authority

Missing, stale, ambiguous, or unsupported source proof cannot grant a reusable schedule.

Recovery stays source-owned

Expectedness never clears an alert. Only authoritative source clearance plus the existing grace period can recover the Situation.

4. What the operator sees

Slack

Root: current lifecycle/status, Finding, operator expectedness when applicable, next real checkpoint, and alert summary.

Thread: investigation result, expectedness applied/stopped/removed, material alert changes, recovery confirmation, and delivery-gap recovery. Technical schedule IDs and routine review machinery stay in MCP.

MCP

Use current reads to answer “what is true now?” Use transition and judgment/history reads to answer “what changed, when, and why?” Current configuration must never be used to invent historical source versions.

Delivery and observation reads show whether evidence was absent, unavailable, unsupported, stale, or successfully empty.

5. Worked example

Nightly reconciliation raises CPU load

22:07 — Alertmanager sends a firing alert for service=payments. AlertINT commits it, opens a Situation, gathers evidence, and publishes the Finding.

22:12 — John marks the current condition expected until 23:00. Slack adds: Operator: Expected until 11:00 PM · John. Investigation and monitoring continue.

22:30 — The same condition repeats unchanged. It remains covered without asking John again.

22:41 — The source rule changes. The decision stops applying. The thread says: The expected-until decision no longer applies because the source rule changed. Normal assessment resumes.

22:50 — The source clears. AlertINT enters Confirming recovery. Only after the stored grace period passes with the alert still clear does the Situation become Recovered.

23:20 — A later firing opens a new linked Situation. It inherits history, not expectedness authority.
